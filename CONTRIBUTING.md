# Help make Fare Signal better

Small, clear changes are welcome. Think of fixing one little piece of a toy at a time.

1. Say what is confusing or broken. Give an example.
2. Change the smallest part that solves it. Keep the page and tests using the same rules.
3. If a rule changes, add a test that asks whether the new rule works.
4. Run `npm test`, `npm run check` and `npm run build` from the project folder.
5. If you change the page, try a first check, a repeat check and the unsure examples. Try a narrow screen and moving between controls with the Tab key.

To suggest a change on GitHub, open a **pull request**. That is a request for someone to look at your changes before adding them. Say what changed, why, what you checked and what you are still unsure about.

Use simple words in the guides and on the page. Explain a technical word the first time you need it. Keep exact file names and commands so people can follow the steps.

Keep this a pretend example. Do not add real keys, private trips, tracking or real messages. If you propose a real connection, make it a separate optional piece and explain its inputs and outputs. Keep keys outside the code. Add extra packages only when they solve a clear problem.

Never share a secret to show how a bug happens. See [keep secrets safe](SECURITY.md) and [be kind](CODE_OF_CONDUCT.md).
